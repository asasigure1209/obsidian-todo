# Obsidian カンバンTODO アーキテクチャ

- 作成日：2026-11-04
- 状態：主要な意思決定が完了。実装はこれから
- 前提：要件と仕様は [design.md](design.md) を正とする。このドキュメントは「どう作るか」の決定と理由を残す

---

## 1. 全体像

```
        ┌────────────── Claude（朝） ──────────────┐
        │ Googleカレンダーを取得し、その日の          │
        │ TODO/YYYY-MM-DD.md を作る（複製・予定・追加）│
        └──────────────────┬───────────────────────┘
                           │ ファイルを書く
                           ▼
┌───────────────────── Vault（Markdown が唯一の正） ─────────────────────┐
│  TODO/YYYY-MM-DD.md      作業ログ/YYYY-MM-DD.md      日報/YYYY-MM-DD.md   │
└───────────────▲──────────────────┬────────────────────────────────────┘
                │ vault.process    │ 変更イベント
┌───────────────┴──────────────────▼──── プラグイン ──────────────────────┐
│  UI層（Svelte）        ボード、M2〜M4 ダイアログ                          │
│     │ コマンド ▲ 表示用モデル                                              │
│  アプリケーション層    コマンドを最新の本文に適用し、書き戻す                    │
│     │                                                                    │
│  ドメイン層（純粋TS）  Markdown の読み書き／状態遷移／タイマー／複製／時間計算  │
│                                                                          │
│  アダプタ層            Vault・設定とタイマーの保存・通知と音・時計            │
└──────────────────────────────────────────────────────────────────────┘
```

**データの流れは一方向。** 操作 → コマンド → 最新の本文に適用 → 書き戻す → 変更イベント → 読み直して再表示。UI は独自の状態を持たない（ダイアログの入力途中の値と、タイマー・タイムラインの表示のための現在時刻だけは例外。時刻はボードと同じ時計から読む）。操作の直後に新しい並びを先に出す「先読み」の表示は、UI ではなく `app/` が持つ（AD-3）。

---

## 2. 決定事項

### AD-1 層を4つに分け、ドメイン層は Obsidian に依存させない

- **決定：** ドメイン層／アプリケーション層／アダプタ層／UI層に分ける。ドメイン層は `obsidian` パッケージを import しない
- **理由：** 仕様の中心はルール（状態遷移、タイマー、複製、時間計算、書式の保持）。Obsidian を起動せずに単体テストできる形にする
- **影響：** 現在時刻もアダプタ（時計）から渡し、ドメイン層の関数は時刻を引数で受け取る

### AD-2 Markdown を唯一の正とし、表示は毎回 Markdown から作る

- **決定：** プラグインは TODO のデータをメモリ上で「正」として持たない。ファイルの変更イベントを受けるたびに読み直し、表示を作り直す
- **理由：** 直接編集の反映（design 8.4）と、Claude による書き込みの反映を、同じ仕組みで扱える。キャッシュと本文がずれる不具合を構造的に防ぐ
- **影響：**
  - 1日のファイルは数十行程度なので、毎回読み直しても性能上の問題はない
  - 本文から表示用のモデル（3列のカード）を作るのは `domain/board.ts` の純粋な関数。カードは `LineRef` を持ち、そのままコマンドに渡せる。直接編集で `[/]` が2件になっても、カードを消さずに両方を着手中に出す
  - カードは表示用の `key`（行の文字列と、同じ文字列の何件目か）も持つ。`LineRef` の位置は上に行が増えるとずれるため、表示の上で同じカードを見分けるのには使わない
  - `app/board/session.ts` の `openBoard` が返す窓口（`BoardSession`）が、変更イベントのたびに読み直して状態（読み込み中・ファイルなし・読めない・ボード）を流す。読み込みは非同期で追い越されることがあるため、最後に始めた読み込みの結果だけを流す（`app/board/reader.ts`）。書き込み中と閉じた後に終わった読み込みは session が捨てる。読めなかったときは前の状態のまま次の変更を待ち、まだ何も読めていなければ「読めない」を流す。受け取る側の例外と、本文の解釈で起きた例外は呼び出し元に渡し（「読めない」にはしない）、次の変更も受け取れるようにする
  - 変更の直後に読むので、キャッシュ（`cachedRead`）ではなく `vault.read` で読む
  - ボードは開いた日で固定するが、「今日のボードを開く」で開き直したときは今日に切り替える
  - ヘッダーの「前の日」「次の日」は `BoardView.showDay` で日を切り替える。今の session とボードを閉じて（開いているダイアログも閉じる）、その日の `openBoard` で作り直す。閉じてから作るまでを同期で行う（トランジションを使わないので、Svelte の unmount はその場で終わる）ので、素早く押してもボードを2つ作らない。表示のための現在時刻は Board が毎秒読み、ヘッダー・タイムライン・「＋ TODOを追加」が同じ「今日」で切り替わる（追加は書き込むときに session も確かめる）。未来の日は開かない（`domain/day.ts` の `canOpen`）
  - タブの見出しは `getDisplayText` が表示している日から作る。切り替えたら見出しを読み直させる（公開の型にない `leaf.updateHeader` を、あれば呼ぶ）
  - ヘッダーの集中ポモドーロ数は、表示用のモデル（`dayPomodoros`）と予定（`dayPomodoroCapacity`）から UI が組み立てる。作業ログは `workspace.openLinkText` で開き、中身は読まない
  - `BoardSession` は Svelte のストアの約束（`subscribe` がすぐに今の値を渡し、購読をやめる関数を返す）と同じ形で返す。`app/` は `svelte` を import せずに済み、`.svelte` 側は `$` を付けて読むだけになる
  - ファイルの取得元は `domain/day-files.ts` の `DayFiles` 型で表し、実体は `adapters/vault.ts`。テストでは手書きの偽物（`tests/app/fakes/`）を使う

### AD-3 書き込みは「最新の本文に変換を当てる」方式にする

- **決定：** 書き込みはすべて `vault.process(file, (本文) => 新しい本文)` で行う。手元の古いコピーで上書きしない
- **理由：** エディタでの直接編集や Claude の書き込みと重なっても、相手の変更を消さない
- **影響：**
  - コマンドは「本文 → 本文」の純粋な関数としてドメイン層に置ける（`commands/`）。コマンドは日付を知らない。過去の日に許される操作か（design 8.3）は `board/session.ts` が判定する
  - 改行は書き戻し（`serializeDocument`）で決める。本文の途中に改行のない行を残さず、末尾に改行がない本文は動かした後も末尾に改行を付けない（最後になった行が空行なら付ける）。コマンドは改行を気にしない
  - 書き戻して読み直すと区切りが変わる結果（先頭に来た `---` が frontmatter になる、など）は、`applyToBody` が書き込まずに何もしない
  - 何もしなかったときは理由を返す。`stale`（対象が最新の本文と一致しない）、`invalid`（入力が書式にならない）、`unstable`（読み直すと区切りが変わる）。`board/session.ts` が知らせ方を決める（`stale` も知らせる。黙って取りやめると、ドラッグが効かなかったように見えるため）
  - **先読み：** 操作を受けたら、最後に読んだ本文にコマンドを当てた結果をすぐに流してから書き込む。書き込みの往復を待つと、ドロップの直後に一瞬元の並びに戻って見えるため。先読みの段階で断られる操作は先読みしない
  - **書き込みは1本に並べる：** 素早く2回操作したとき、2回目の対象（`LineRef`）は1回目の先読みの結果から取っている。1回目を書き終えてから2回目を当てて、対象をずらさない。書き込みが残っているうちの読み直しの結果は捨て、書き込みのたびに読み直す（断られて本文が変わらないときも、先読みの表示を元に戻すため）。タイマーの確定（AD-6）もこの並びに乗せる
  - 書き込みが断られたとき（書き込みの失敗も含む）は、それより前に受けて並んでいる操作を書き込まずに捨てる。どれも断られた操作の先読みをもとにしているので、当てても `stale` になり、同じ通知が続くだけだから
  - 書き込みに失敗したときも知らせる（「ファイルに書き込めませんでした」）。例外は `onError` にも渡す
  - 取りやめて本文が変わらないときは、ファイルに書き込まない（`adapters/vault.ts`）。同期ツールや開いているエディタに、変わっていない書き込みを見せないため

### AD-4 書き戻しで元の内容を壊さない読み書きにする

- **決定：**
  - 本文を「frontmatter」と、次の2種類のまとまりの並びとして読む
    - **TODOブロック：** トップレベルの TODO 行と、それより深く字下げされた後続の行すべて。作業時間の子の行のほか、書式外の行（字下げしたメモなど）も含む
    - **固定行：** どの TODO ブロックにも属さない行（トップレベルの書式外の行、空行など）
  - 固定行と、TODO ブロック内の書式外の行は、中身を解釈しない
  - 読んでそのまま書き戻すと、元の本文と完全に一致することをテストで保証する
- **理由：** design 8.4「書式から外れた行は無視してそのまま残す」を確実に守る。改行コードやインデントの揺れも変えない。TODO の下に書いたメモが、並べ替えでカードから外れないようにする
- **影響：**
  - 並べ替え・状態の変更・追加は、**TODO ブロック単位**で動かす。固定行は元の位置から動かさない
  - 書き戻すときは、触れていない TODO ブロックと固定行を一字も変えない
  - 列の端の位置は、実際の行の上で次のように決める
    - 「今日やるの先頭」：最初の `[ ]` ブロックの直前
    - 「今日やるの末尾」：最後の `[ ]` ブロックの直後
    - `[ ]` のブロックが1つもないとき：どちらも、最後の TODO ブロックの直後（TODO が1件もなければ本文の末尾）

### AD-5 TODO の ID は Markdown に書かない

- **決定：** 行にブロックIDなどは付けない。操作時は「行の位置と、その行の文字列」で対象を特定する。本文を開いた時点で一致しなければ処理を中止し、読み直して再表示する
- **理由：** Markdown の見た目を保つ（P2）。1日の件数は少なく、同名の TODO が並ぶことはまれ
- **影響：** 同じ文字列の TODO が複数あっても、位置で区別できる。ずれたときは「何もしない」に倒し、データを壊さない

### AD-6 タイマーの状態は「日付・開始時刻・対象の行の文字列」を保存し、確定の書き込みは1本に並べる

- **決定：**
  - 計測中の状態として `{ 日付, 開始時刻, 対象の行の文字列 }` をプラグインの保存領域に置く。残り時間は毎秒「現在時刻 − 開始時刻」で計算する
  - 対象の TODO は、その日のファイルにただ1つある `[/]` の行で、かつ文字列が保存したものと一致する行とする
  - **確定（経過分を Markdown に書く）処理は1本に並べる。** 25分の満了、中断、完了、別のカードへの切り替えなど、タイマーの状態を変える操作は、確定処理の実行中は待たせて順番に処理する
  - 確定は「タイマーの状態を先に消す → Markdown に書く」の順で行う
  - 対象の行が見つからない（`[/]` が0件・2件、または文字列が違う）ときは、すぐには破棄せず**保留**にする。次の操作か25分の満了の時点で改めて判定し、それでも見つからなければ破棄して Obsidian 内の通知で知らせる
- **理由：**
  - 着手中は常に1件なので ID がなくても対象が決まる（AD-5 と両立）。スリープや再起動後の再計算（design 8.1）が同じ計算で済む
  - 書き込みは非同期なので、並べないと毎秒の判定や満了と「完了にする」の重なりで、同じ記録が2行書かれる
  - Markdown とタイマーの状態は1回の書き込みにまとめられない。途中で失敗したとき、二重に記録されるより欠けるほうがよい（欠けた分は M2 で直せる。二重の記録は気づきにくい）
  - エディタで `[/]` を打ち直している途中など、一時的な崩れで計測を捨てると、前職と同じ「記録が欠けて信用されない」失敗になる。文字列を持つことで、`[/]` を別の行へ付け替えたときに別のカードへ記録することも防ぐ
- **影響：**
  - 破棄した場合、経過分は記録しない。通知を見た本人が M2 で直す
  - 状態遷移は `domain/timer.ts` の `stepTimer` が純粋な関数で行う。「タイマー＋きっかけ＋本文＋現在時刻」から「次のタイマー＋変更後の本文＋知らせること」を返し、記録とカードの移動を1回の書き込みにまとめる
  - 書き込みとタイマーの窓口は `app/day-editor.ts` の `DayEditor` で、プラグインに1つだけ置く。ボードの操作もタイマーの確定も、すべてこの並びに乗せる。1回の操作は「最新の本文を読む → `stepTimer` → タイマーを保存 → 読んだときの本文のままなら書き換える」。読んでから書くまでに本文が変わっていたり、書き込みに失敗したりしたら、書かずにタイマーを元に戻す
  - 毎秒の判定（`tick`）は `main.ts` の `registerInterval` で回すので、ボードを閉じていても進む。Vault の準備ができてから（`onLayoutReady`）始め、最初の判定で、スリープ中や閉じていた間の満了も確定する。保留中は毎秒の判定をせず、タイマーの日のファイルが変わるたびに読み直す（編集中は変更が続くので、読み直しは並びに1つだけ置く）
  - 満了を確定できなかったとき（ファイルがない、書き込めない）は、タイマーが元のまま残るので保留にする。毎秒やり直して通知が出続けないようにする
  - タイマーは、保存できてからメモリ上の値を持ち替える。保存に失敗したら今のタイマーを変えずに断る
  - ほかの日のタイマーに中断を記録できなかったとき（対象が見つからない）は、新しい計測で置き換える前に捨てて知らせる
  - ほかの日のタイマーが残っているときに新しく計測を始めると、先にその日のファイルへ中断を記録する（日付をまたいで計測したとき）
  - 「この日のタイマーとその対象」（`runningTarget`）と満了の判定（`isDue`）は `domain/timer.ts` に1つだけ置き、`stepTimer`・`DayEditor`・ボードで共有する。ボードの先読みも、書き込みと同じ `stepTimer` を最後に読んだ本文に当てる（記録の行も先に出る）
  - ボードは計測中のカードを、表示を組み立てるたびに `DayEditor` の今のタイマーから求める。タイマーが変わる操作の後は必ず読み直すので、タイマーの変化を購読しなくてよい
  - タイマーを動かさない本文だけの変更（M2 の保存、M4 の追加）も、`stepTimer` のきっかけ `edit`（本文へのコマンドを持つ）として同じ並びに乗せる。タイマーは変えず、対象の判定もしない
  - M2 の保存は `domain/commands/work.ts` の `editWork` で1回の変更にまとめる。どの位置も変える前の子の行で探すので、当てる順番に左右されない。開いた後にタイマーが足した記録は末尾に増えるだけなので、開いたときの位置のまま当たる
  - 保存先はプラグインの保存領域（`data.json` の `timer`）。設定と1つのファイルを分け合う（AD-11）。読んだ値の形が合わなければ停止中として扱う（`parseTimer`）

### AD-7 UI は Svelte で作り、独自のビューとして開く

- **決定：** Svelte でボードとダイアログを作る。Obsidian の独自ビュー（タブ）として開く。並べ替えのドラッグは SortableJS を使う
- **理由：** 出力が小さく、Obsidian の公式ドキュメントにも組み込み方の案内がある。3列のボードとサイドバーの広さが要るため、独自ビューにする
- **影響：**
  - 色は Obsidian の CSS 変数を使い、本体のテーマに追従させる（design 5章「テーマ」）
  - SortableJS が動かした DOM は、ドロップの直後に元の位置へ戻す（`ui/sortable.ts`）。並びは Markdown を書き換えて読み直した結果（と先読み）で Svelte が描く。DOM を書き換える主体を Svelte だけにして、keyed each とぶつからないようにする（試作 `spike/sortable` で確認）
  - 着手中の列の中の並べ替えは何もしない。着手中には列の中の位置がなく（design 8.6）、着手中への移動として扱うと、ほかの着手中を今日やるへ戻してしまうため

### AD-8 予定とその日のファイルの作成は Claude が担う。プラグインは Google に接続しない

- **決定：**
  - 朝、本人の指示で Claude が Googleカレンダーを取得し、その日の TODO ファイルを作る。前日の未完了の複製、予定、追加の TODO を書く
  - 予定は TODO ファイルの frontmatter の `events` に書く
  - プラグインは予定を読んで表示するだけ。Google との認証や通信は持たない
  - その日のファイルがない場合、プラグインは自動では作らない。代わりに「今日のファイルを作る」ボタンを出し、押すと複製のルール（design 7.8）だけで作る。Claude を使わない日のための予備
- **理由：** 本人が朝に Claude と TODO を組み立てる運用を想定している。プラグインから認証の仕組みと秘密の情報をなくせるので、実装が大きく軽くなる。作る主体を Claude に1本化して、どちらが先に作ったかで結果が変わる状態を避ける
- **影響：**
  - 複製のルールは、Claude とプラグインの2か所で守る必要がある。ルールは design 7.8 を正とする
  - 日中に予定が変わったら、Claude に頼んで `events` を書き直してもらう
  - **「今日のファイルを作る」の作り：**
    - 複製は `domain/carryover.ts` の純粋な関数。`latestDayBefore` がファイル名の一覧から直近の過去ファイルの日を1回の走査で選び（`day.ts` の `dayKeyOfFileName` で `YYYY-MM-DD.md` の暦にある日だけ。今日より前でいちばん新しい日。ファイル名の決まりは `dayFileName` と合わせて day.ts の1か所に置く）、`carryOver` が過去ファイルの本文から今日の本文を作る。本文は `document/body.ts` で読み、作った `DayDocument` を `serializeDocument` で書くので、ボードが読むのと同じ区切りになる（読んで戻すと一致することを性質で確かめる）。過去ファイルがなければ空の本文を渡す
    - TODO 行は `formatTodoLine` で `[ ]` にして書き直す（名前と見積もりはそのまま）。子の行は、`parseWorkEntry` で読める作業時間の行と、それに続くより深く字下げされた行（作業時間の行に付けたメモ）を外し、ほかは文字列のまま残す。より深いとは、字下げが作業時間の行の字下げで始まり、それより長いこと（タブとスペースが混ざっても決まる）。作業時間ではない子の行の下の行は残す。改行は過去ファイルで最初に使われている改行に合わせ、末尾に改行を付ける
    - `DayFiles` に `list()`（TODO のフォルダの直下のファイル名）と `create(dayKey, body)`（もうあれば上書きせずに false）を足す。どの名前が日のファイルかは domain が決め、`adapters/vault.ts` はフォルダの子を返すだけにする（下のフォルダの中は見ない）。「ある」は Obsidian の索引に加えて `vault.adapter.exists` でディスクも見る（Claude がディスクに直接書いて、まだ索引されていないファイルを上書きしない）。`create` は TODO のフォルダがなければ先に作る。確かめてから作るまでに別の書き手がファイルやフォルダを作って `vault.create`・`createFolder` が失敗したときも、確かめ直してあれば、ファイルは false、フォルダはそのまま続ける
    - 窓口は `BoardSession.createToday`。今日のボードだけ（`canEdit` の `create`。過去の日は断って知らせる）。「一覧 → 過去ファイルを読む → 作る」の順で、作れたら作成の変更イベントで読み直してボードに出す。もうあったら知らせて読み直す（あったファイルを出す）。一覧・読み込み・作成のどこで失敗しても作らずに知らせ、例外は `onError` へ
    - 書き込みの並び（`DayEditor`。AD-3・AD-6）には乗せない。まだないファイルを作るだけで、並びに乗る書き込み（ある日のファイルの `vault.process`）と対象が重ならないため。上書きしないことは `create` が守る
    - 作っている間にもう一度押されても何もしない（2回目が「もうあった」と知らせないように）。ボードも作っている間はボタンを押せなくする
    - 待っている間にボードを閉じたら、知らせも読み直しもしない（例外は `onError` へ渡す）。閉じているかと、その日にできる操作かの確かめは、ほかの操作と同じ `allowed` で行う
    - 一覧を見てから読むまでに過去ファイルが消えたときは、過去ファイルがないものとして frontmatter だけで作る

### AD-9 ビルドは公式サンプルの構成、テストは Vitest

- **決定：** TypeScript＋esbuild（Obsidian の公式サンプルプラグインに準拠）。テストは Vitest で、TDD で書く。プロパティベーステストに fast-check、ミューテーションテストに Stryker を使う。UI は手動の確認手順で確かめる（詳細は [test-strategy.md](test-strategy.md)）
- **理由：** 標準的な構成で迷う要素を減らす。不具合が起きると困るのはデータとタイマーのルールなので、そこに厚くテストを書く

### AD-10 コード品質は Biome 1つで守り、コミット前と CI の2か所で止める

- **決定：**
  - 整形と Lint は Biome だけで行う（Prettier・ESLint は使わない）
  - 認知複雑度の上限は **5**（テストコードは対象外）
  - 層の境界も Biome の `noRestrictedImports` で守る。層ごとに禁止する import を設定する（下の表）
  - 層をまたぐ import は `@/層名/...` の別名で書く。`../` で始まる import は禁止する（相対パスだと層の判定をすり抜けるため）
  - 循環参照は Biome の `noImportCycles` で禁止する
  - コミット前は lefthook でコミットするファイルだけを検査し、直せるものは直して取り込む。push と PR では GitHub Actions で全項目（整形・Lint・境界、型、テストとカバレッジ、ビルド）を実行する
- **理由：** 道具を1つにして設定と依存を減らす。複雑度を低く抑えて、ルールを遷移表と小さな関数で書くことを促す。境界の違反を、レビューではなく機械で止める
- **影響：**
  - Obsidian 公式の lint ルール（ESLint 専用）は使えない。コミュニティストアに公開する段階で改めて検討する
  - Biome の Svelte 対応は試験段階。誤検出が出たら `.svelte` ファイルだけ該当ルールを外す
  - 「型だけ import してよい」（`adapters/` → `domain/`）は Biome では区別できないため、レビューで守る。`ui/` → `domain/` は、型に加えて副作用のない関数（表示の組み立て、M2 の下書き、入力の確かめ）も使ってよい。決まりを domain の1か所に置き、表示と書き込みで食い違わないようにするため
  - Markdown は Biome の対象外（日本語の表が崩れるため）
  - `ui/` で `obsidian` を使えるのは、Obsidian との境目になる2つのファイルだけ。独自ビュー（`BoardView.ts`）と設定画面（`SettingsTab.ts`）。設定画面は `PluginSettingTab` と `Setting` で Obsidian の標準の見た目にするため、`obsidian` が要る。画面なので `ui/` に置き、`adapters/` には置かない（`adapters/` は `app/` を import できず、設定の窓口 `AppSettings` を使えない）。Biome の override は options を置き換えるので、この override にも共通の `../` 禁止を書く（`tests/config/biome-boundaries.test.ts` が、この2つだけに許していることも確かめる）

| 層 | import してよいもの | `obsidian` | `svelte` |
|---|---|---|---|
| `domain/` | なし | 禁止 | 禁止 |
| `app/` | `domain/`, `adapters/` | 禁止 | 禁止 |
| `adapters/` | `domain/` | 許可 | 許可 |
| `ui/` | `app/`, `domain/` | `BoardView.ts` と `SettingsTab.ts` だけ許可（`.svelte` では禁止） | 許可 |
| `main.ts` | すべて | 許可 | 許可 |

### AD-11 設定は data.json をタイマーと分け合い、使う時点で今の設定から読む

- **決定：**
  - 設定（フォルダ・就業時間と休憩・満了の音。design 5章「設定画面」）は、プラグインの保存領域（`data.json`）の `settings` に置く。タイマーの `timer`（AD-6）と同じファイル
  - `data.json` の読み書きは `adapters/plugin-data.ts` の `PluginData` 1か所にまとめる。書き込みは「読む → 1つの項目だけ差し替える → 書く」を1本に並べる。タイマーの保存（`PluginTimerStore`）と設定の保存（`PluginSettingsStore`）は、どちらもこれを通す
  - 設定の型、既定値（`DEFAULT_SETTINGS`）、読んだ値の検査（`parseSettings`）、入力の確かめ（`readFolder`・`readWorkday`）は `domain/settings.ts` に置く。時刻の入力は `domain/schedule.ts` の `parseClock` で読む（予定の行と同じ、ありえない時刻を読まない決まり）
  - 設定の窓口は `app/settings.ts` の `AppSettings` で、プラグインに1つ。Svelte のストアと同じ形（`subscribe`）で今の設定を流し、`current()` で今の設定を返す。`update` は変えた設定をすぐに流してから保存する（変わらなければ流しも保存もしない）。`watch` は選んだ部分が変わったときだけ呼ぶ
  - 使う側は、使う時点で今の設定を読む
    - `VaultDayFiles`（`adapters/vault.ts`）は TODO のフォルダを関数で受け取り、読み書きと変更イベントのたびにパスを求める
    - 満了の音（`adapters/notifier.ts` の `expiryAlarm`）は、鳴らすときに音の有無を読む
    - 作業ログのリンク（`BoardView`）は、開くときにフォルダを読む
  - TODO のフォルダが変わったら、`main.ts` が `watch` で `VaultDayFiles.folderChanged()` を呼ぶ。購読中の受け取り手すべてにファイルの変更として知らせるので、ボードは新しいフォルダのファイルを読み直し、保留中のタイマー（AD-6）も新しいファイルで判定し直す
  - 就業時間と休憩は、Board が設定（`Readable<Settings>`）から読み、変わったらその場で描き直す。ボードは作り直さない
  - 設定画面（`ui/SettingsTab.ts`）は入力のたびに確かめて問題を出し、打ち終えたとき（Enter や欄を離れたとき）に正しければ `update` に渡す。打つたびに渡すと、日本語入力の途中や打ちかけの値で読み直してしまう。就業時間と休憩は組み合わせで確かめるので、入力の途中の値（`WorkdayDraft`）を設定画面が持つ
- **理由：**
  - タイマーと設定を別々に「読んで書く」と、両方が同じ古い中身を読み、後から書いたほうが先の項目を消す。並べる場所を1つにすれば、どちらの保存も相手の項目を消さない
  - `adapters/` は `domain/` の値を import しない（AD-10）。そのため `PluginSettingsStore` は読んだままの値を返し、形の検査は `app/` が `parseSettings` で行う（`parseTimer` と同じく項目ごとに既定値へ倒すが、決まりを domain の1か所に置いてテストする）
  - 使う時点で読めば、設定を変えた後に購読を張り直さなくてよい。`VaultDayFiles` はボードと `DayEditor`（計測中の日のファイルを見張る。AD-6）が分け合うので、張り直さずに新しいフォルダの変更を知らせられるほうが壊れにくい
  - フォルダの変更を「ファイルの変更」として知らせれば、ボードもタイマーも、すでにある読み直しの道をそのまま通る。受け取り手ごとに後始末を足さずに済む
- **影響：**
  - 設定を変えても、開いている M2・M4 のダイアログは閉じない
  - 保存できなかったときは知らせ、変えた設定はそのまま使う（開き直すと前の設定に戻る）
  - 保存領域が読めないときは既定値で開く。設定が読めないだけで、ボードとタイマーを止めない
  - 計測中に TODO のフォルダを変えると、タイマーは新しいフォルダの同じ日付のファイルで対象を探す。見つからなければ保留にする（AD-6）。フォルダの変更では変更イベントが来ないので、保留の読み直しは次の変更か操作のとき
  - 設定画面は入力のたびに保存する（`data.json` に書く回数は増えるが、書き込みは並べてあるので順番どおりに残る）

## 4. 開発環境

### 準備

```bash
mise install          # Node 24
pnpm install          # 依存とコミット前のフック（lefthook）を入れる
pnpm dev              # build/ へ監視ビルド
```

- 動作確認は `dev-vault/` を Obsidian で Vault として開いて行う。`dev-vault/.obsidian/plugins/daily-kanban-todo` は `build/` へのシンボリックリンク
- 変更をすぐ反映させるには、`dev-vault` に Hot Reload プラグイン（pjeby/hot-reload）を本人が入れる。`pnpm dev` が `build/.hotreload` を作るので、ビルドのたびに再読み込みされる
- `dev-vault/TODO/` には、書式外の行・字下げしたメモ・`events` を含むサンプルを置いている

### コマンド

| コマンド | 内容 |
|---|---|
| `pnpm check` / `pnpm fix` | Biome の整形・Lint・境界の検査／自動修正 |
| `pnpm typecheck` | `svelte-check`（`.ts` も含めて型を検査） |
| `pnpm test` / `pnpm coverage` | Vitest。カバレッジは `src/domain/` に 90% の下限 |
| `pnpm mutation` | Stryker で `src/domain/` のミューテーションテスト（下限 80%。CI では回さない） |
| `pnpm build` | 本番ビルド（`build/`） |
| `pnpm verify` | 上の全部（CI と同じ） |

## 6. 実装しながら決めること

| 論点 | 方針の目安 |
|---|---|
| ボードを開いたまま日付が変わった場合 | 自動では切り替えない。日付の表示で気づけるようにする |
| 配布 | 当面は自分の Vault に直接入れる。公開するかは後で決める |
| Claude 向けの手順 | 朝のファイル作成の手順（複製のルールと `events` の書式）を Claude 用のスキルとしてまとめるかは、実際に運用してから決める |
