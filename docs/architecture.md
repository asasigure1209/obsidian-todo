# Obsidian カンバンTODO アーキテクチャ

- 作成日：2026-11-04
- 状態：主要な意思決定が完了。実装はこれから
- 前提：要件と仕様は [design.md](design.md) を正とする。このドキュメントは「どう作るか」の決定と理由を残す

---

## 1. 全体像

```
        ┌────────────── Claude（朝） ──────────────┐
        │ Googleカレンダーを取得し、その日の          │
        │ TODO/YYYY-MM-DD.md を作る（複製・予定・追加）│
        └──────────────────┬───────────────────────┘
                           │ ファイルを書く
                           ▼
┌───────────────────── Vault（Markdown が唯一の正） ─────────────────────┐
│  TODO/YYYY-MM-DD.md      作業ログ/YYYY-MM-DD.md      日報/YYYY-MM-DD.md   │
└───────────────▲──────────────────┬────────────────────────────────────┘
                │ vault.process    │ 変更イベント
┌───────────────┴──────────────────▼──── プラグイン ──────────────────────┐
│  UI層（Svelte）        ボード、M2〜M4 ダイアログ                          │
│     │ コマンド ▲ 表示用モデル                                              │
│  アプリケーション層    コマンドを最新の本文に適用し、書き戻す                    │
│     │                                                                    │
│  ドメイン層（純粋TS）  Markdown の読み書き／状態遷移／タイマー／複製／時間計算  │
│                                                                          │
│  アダプタ層            Vault・設定とタイマーの保存・通知と音・時計            │
└──────────────────────────────────────────────────────────────────────┘
```

**データの流れは一方向。** 操作 → コマンド → 最新の本文に適用 → 書き戻す → 変更イベント → 読み直して再表示。UI は独自の状態を持たない（ダイアログの入力途中の値と、タイマーの表示だけは例外）。

---

## 2. 決定事項

### AD-1 層を4つに分け、ドメイン層は Obsidian に依存させない

- **決定：** ドメイン層／アプリケーション層／アダプタ層／UI層に分ける。ドメイン層は `obsidian` パッケージを import しない
- **理由：** 仕様の中心はルール（状態遷移、タイマー、複製、時間計算、書式の保持）。Obsidian を起動せずに単体テストできる形にする
- **影響：** 現在時刻もアダプタ（時計）から渡し、ドメイン層の関数は時刻を引数で受け取る

### AD-2 Markdown を唯一の正とし、表示は毎回 Markdown から作る

- **決定：** プラグインは TODO のデータをメモリ上で「正」として持たない。ファイルの変更イベントを受けるたびに読み直し、表示を作り直す
- **理由：** 直接編集の反映（design 8.4）と、Claude による書き込みの反映を、同じ仕組みで扱える。キャッシュと本文がずれる不具合を構造的に防ぐ
- **影響：** 1日のファイルは数十行程度なので、毎回読み直しても性能上の問題はない

### AD-3 書き込みは「最新の本文に変換を当てる」方式にする

- **決定：** 書き込みはすべて `vault.process(file, (本文) => 新しい本文)` で行う。手元の古いコピーで上書きしない
- **理由：** エディタでの直接編集や Claude の書き込みと重なっても、相手の変更を消さない
- **影響：** コマンドは「本文 → 本文」の純粋な関数としてドメイン層に置ける

### AD-4 書き戻しで元の内容を壊さない読み書きにする

- **決定：**
  - 本文を「frontmatter」と、次の2種類のまとまりの並びとして読む
    - **TODOブロック：** トップレベルの TODO 行と、それより深く字下げされた後続の行すべて。作業時間の子の行のほか、書式外の行（字下げしたメモなど）も含む
    - **固定行：** どの TODO ブロックにも属さない行（トップレベルの書式外の行、空行など）
  - 固定行と、TODO ブロック内の書式外の行は、中身を解釈しない
  - 読んでそのまま書き戻すと、元の本文と完全に一致することをテストで保証する
- **理由：** design 8.4「書式から外れた行は無視してそのまま残す」を確実に守る。改行コードやインデントの揺れも変えない。TODO の下に書いたメモが、並べ替えでカードから外れないようにする
- **影響：**
  - 並べ替え・状態の変更・追加は、**TODO ブロック単位**で動かす。固定行は元の位置から動かさない
  - 書き戻すときは、触れていない TODO ブロックと固定行を一字も変えない
  - 列の端の位置は、実際の行の上で次のように決める
    - 「今日やるの先頭」：最初の `[ ]` ブロックの直前
    - 「今日やるの末尾」：最後の `[ ]` ブロックの直後
    - `[ ]` のブロックが1つもないとき：どちらも、最後の TODO ブロックの直後（TODO が1件もなければ本文の末尾）

### AD-5 TODO の ID は Markdown に書かない

- **決定：** 行にブロックIDなどは付けない。操作時は「行の位置と、その行の文字列」で対象を特定する。本文を開いた時点で一致しなければ処理を中止し、読み直して再表示する
- **理由：** Markdown の見た目を保つ（P2）。1日の件数は少なく、同名の TODO が並ぶことはまれ
- **影響：** 同じ文字列の TODO が複数あっても、位置で区別できる。ずれたときは「何もしない」に倒し、データを壊さない

### AD-6 タイマーの状態は「日付・開始時刻・対象の行の文字列」を保存し、確定の書き込みは1本に並べる

- **決定：**
  - 計測中の状態として `{ 日付, 開始時刻, 対象の行の文字列 }` をプラグインの保存領域に置く。残り時間は毎秒「現在時刻 − 開始時刻」で計算する
  - 対象の TODO は、その日のファイルにただ1つある `[/]` の行で、かつ文字列が保存したものと一致する行とする
  - **確定（経過分を Markdown に書く）処理は1本に並べる。** 25分の満了、中断、完了、別のカードへの切り替えなど、タイマーの状態を変える操作は、確定処理の実行中は待たせて順番に処理する
  - 確定は「タイマーの状態を先に消す → Markdown に書く」の順で行う
  - 対象の行が見つからない（`[/]` が0件・2件、または文字列が違う）ときは、すぐには破棄せず**保留**にする。次の操作か25分の満了の時点で改めて判定し、それでも見つからなければ破棄して Obsidian 内の通知で知らせる
- **理由：**
  - 着手中は常に1件なので ID がなくても対象が決まる（AD-5 と両立）。スリープや再起動後の再計算（design 8.1）が同じ計算で済む
  - 書き込みは非同期なので、並べないと毎秒の判定や満了と「完了にする」の重なりで、同じ記録が2行書かれる
  - Markdown とタイマーの状態は1回の書き込みにまとめられない。途中で失敗したとき、二重に記録されるより欠けるほうがよい（欠けた分は M2 で直せる。二重の記録は気づきにくい）
  - エディタで `[/]` を打ち直している途中など、一時的な崩れで計測を捨てると、前職と同じ「記録が欠けて信用されない」失敗になる。文字列を持つことで、`[/]` を別の行へ付け替えたときに別のカードへ記録することも防ぐ
- **影響：** 破棄した場合、経過分は記録しない。通知を見た本人が M2 で直す

### AD-7 UI は Svelte で作り、独自のビューとして開く

- **決定：** Svelte でボードとダイアログを作る。Obsidian の独自ビュー（タブ）として開く。並べ替えのドラッグは専用のライブラリを使う（候補：SortableJS。実装の最初に確かめて決める）
- **理由：** 出力が小さく、Obsidian の公式ドキュメントにも組み込み方の案内がある。3列のボードとサイドバーの広さが要るため、独自ビューにする
- **影響：** 色は Obsidian の CSS 変数を使い、本体のテーマに追従させる（design 5章「テーマ」）

### AD-8 予定とその日のファイルの作成は Claude が担う。プラグインは Google に接続しない

- **決定：**
  - 朝、本人の指示で Claude が Googleカレンダーを取得し、その日の TODO ファイルを作る。前日の未完了の複製、予定、追加の TODO を書く
  - 予定は TODO ファイルの frontmatter の `events` に書く
  - プラグインは予定を読んで表示するだけ。Google との認証や通信は持たない
  - その日のファイルがない場合、プラグインは自動では作らない。代わりに「今日のファイルを作る」ボタンを出し、押すと複製のルール（design 7.8）だけで作る。Claude を使わない日のための予備
- **理由：** 本人が朝に Claude と TODO を組み立てる運用を想定している。プラグインから認証の仕組みと秘密の情報をなくせるので、実装が大きく軽くなる。作る主体を Claude に1本化して、どちらが先に作ったかで結果が変わる状態を避ける
- **影響：**
  - 複製のルールは、Claude とプラグインの2か所で守る必要がある。ルールは design 7.8 を正とする
  - 日中に予定が変わったら、Claude に頼んで `events` を書き直してもらう

### AD-9 ビルドは公式サンプルの構成、テストは Vitest

- **決定：** TypeScript＋esbuild（Obsidian の公式サンプルプラグインに準拠）。テストは Vitest で、ドメイン層を重点的に書く。UI は手動での確認を基本にする
- **理由：** 標準的な構成で迷う要素を減らす。不具合が起きると困るのはデータとタイマーのルールなので、そこに厚くテストを書く

### AD-10 コード品質は Biome 1つで守り、コミット前と CI の2か所で止める

- **決定：**
  - 整形と Lint は Biome だけで行う（Prettier・ESLint は使わない）
  - 認知複雑度の上限は **5**（テストコードは対象外）
  - 層の境界も Biome の `noRestrictedImports` で守る。層ごとに禁止する import を設定する（下の表）
  - 層をまたぐ import は `@/層名/...` の別名で書く。`../` で始まる import は禁止する（相対パスだと層の判定をすり抜けるため）
  - 循環参照は Biome の `noImportCycles` で禁止する
  - コミット前は lefthook でコミットするファイルだけを検査し、直せるものは直して取り込む。push と PR では GitHub Actions で全項目（整形・Lint・境界、型、テストとカバレッジ、ビルド）を実行する
- **理由：** 道具を1つにして設定と依存を減らす。複雑度を低く抑えて、ルールを遷移表と小さな関数で書くことを促す。境界の違反を、レビューではなく機械で止める
- **影響：**
  - Obsidian 公式の lint ルール（ESLint 専用）は使えない。コミュニティストアに公開する段階で改めて検討する
  - Biome の Svelte 対応は試験段階。誤検出が出たら `.svelte` ファイルだけ該当ルールを外す
  - 「型だけ import してよい」（`adapters/` → `domain/`、`ui/` → `domain/`）は Biome では区別できないため、レビューで守る
  - Markdown は Biome の対象外（日本語の表が崩れるため）

| 層 | import してよいもの | `obsidian` | `svelte` |
|---|---|---|---|
| `domain/` | なし | 禁止 | 禁止 |
| `app/` | `domain/`, `adapters/` | 禁止 | 禁止 |
| `adapters/` | `domain/` | 許可 | 許可 |
| `ui/` | `app/`, `domain/` | `BoardView.ts` だけ許可（`.svelte` では禁止） | 許可 |
| `main.ts` | すべて | 許可 | 許可 |

## 3. ディレクトリ構成（案）

```
src/
  main.ts                 プラグインの入口。ビュー・コマンド・設定画面の登録
  domain/                 Obsidian に依存しない
    document.ts           1日のファイルの読み書き（AD-4）
    commands.ts           追加・並べ替え・状態の変更・時間の修正（本文 → 本文）
    timer.ts              タイマーの状態遷移と経過分の計算（AD-6）
    carryover.ts          前日の未完了の複製（design 7.8）
    schedule.ts           予定・就業時間・休憩から、集中できる時間を出す（design 8.2）
    clock.ts              現在時刻の取得元の型（実体は adapters/clock.ts）
  app/
    board-service.ts      コマンドを受け、vault.process で書き戻す（AD-3）
  adapters/
    vault.ts              ファイルの取得・変更イベントの購読
    storage.ts            設定とタイマー状態の保存
    notifier.ts           通知と音
    clock.ts              現在時刻
  ui/
    BoardView.ts          独自ビュー
    *.svelte              ボード、カード、M2〜M4 ダイアログ
tests/
  domain/                 ドメイン層の単体テスト。読み書きの往復テストを含む
```

## 4. 開発環境

### 準備

```bash
mise install          # Node 24
pnpm install          # 依存とコミット前のフック（lefthook）を入れる
pnpm dev              # build/ へ監視ビルド
```

- 動作確認は `dev-vault/` を Obsidian で Vault として開いて行う。`dev-vault/.obsidian/plugins/daily-kanban-todo` は `build/` へのシンボリックリンク
- 変更をすぐ反映させるには、`dev-vault` に Hot Reload プラグイン（pjeby/hot-reload）を本人が入れる。`pnpm dev` が `build/.hotreload` を作るので、ビルドのたびに再読み込みされる
- `dev-vault/TODO/` には、書式外の行・字下げしたメモ・`events` を含むサンプルを置いている

### コマンド

| コマンド | 内容 |
|---|---|
| `pnpm check` / `pnpm fix` | Biome の整形・Lint・境界の検査／自動修正 |
| `pnpm typecheck` | `svelte-check`（`.ts` も含めて型を検査） |
| `pnpm test` / `pnpm coverage` | Vitest。カバレッジは `src/domain/` に 90% の下限 |
| `pnpm build` | 本番ビルド（`build/`） |
| `pnpm verify` | 上の全部（CI と同じ） |

## 5. テストで必ず押さえること

- 読んでそのまま書き戻すと、元の本文と完全に一致する（書式外の行、空行、改行コード、インデント）
- 各コマンドの後も、固定行が元の位置に残る。TODO ブロック内のメモは、並べ替えた後もそのカードの下にある
- 「今日やる」が0件のときの先頭・末尾への移動と追加
- タイマー（design 8.1 の表の各行）：25分の満了、中断、完了、別のカードへの切り替え、スリープ後の再計算、1分未満を記録しない
- タイマーの確定：満了と「完了にする」が重なっても記録は1行だけ。`[/]` が一時的に崩れても保留にして、元に戻れば計測を続ける
- 複製：直近の過去ファイルを選ぶ（週末を挟む）、状態を `[ ]` に戻す、見積もりを残す、作業時間の行をコピーしない、元のファイルを変えない
- 集中できる時間：予定と休憩の重なり、就業時間外、端数の切り捨て

## 6. 実装しながら決めること

| 論点 | 方針の目安 |
|---|---|
| ボードを開いたまま日付が変わった場合 | 自動では切り替えない。日付の表示で気づけるようにする |
| 通知音の作り方 | 音声ファイルを同梱せず、ブラウザの音声機能で短い音を鳴らす方向 |
| 配布 | 当面は自分の Vault に直接入れる。公開するかは後で決める |
| ドラッグのライブラリ | SortableJS を第一候補に、Svelte との相性を最初に確かめる |
| Claude 向けの手順 | 朝のファイル作成の手順（複製のルールと `events` の書式）を Claude 用のスキルとしてまとめるかは、実際に運用してから決める |
