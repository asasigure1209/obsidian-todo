# Obsidian カンバンTODO テスト戦略

- 作成日：2026-11-04
- 前提：仕様は [design.md](design.md)、層と決定は [architecture.md](architecture.md) を正とする
- 参考：t-wada（和田卓人）氏の TDD の考え方（Kent Beck『テスト駆動開発』の訳者解説・講演）

---

## 1. 方針

- **テスト駆動開発（TDD）で書く。** 目的は「動作するきれいなコード」。テストを先に書き、小さな歩幅で進める
- **テストは動く仕様書。** テスト名は日本語で、design.md の言葉を使う。読めば仕様が分かることを目指す
- **テストコードもプロダクトコード。** 読みやすさを保ち、リファクタリングの対象にする（認知複雑度の上限はテストには適用しないが、分かりにくい準備処理はヘルパーに切り出す）
- **速いテストを大量に、遅いテストを少し。** 手元で数秒以内に全件が終わる状態を保つ

---

## 2. TDD の進め方

### 2.1 サイクル

1. **TODOリストを書く。** 実装したい振る舞いを、テストファイルに `it.todo("…")` として並べる。思いついたことはサイクルの途中でも足す
2. **Red：** TODO を1つ選んで失敗するテストにする。実行して、**想定どおりの理由で**失敗することを確かめる（型エラーや import の失敗で落ちているのは Red ではない）
3. **Green：** 最短で通す。歩幅は自信に合わせて変える
   - **仮実装：** まずは期待値をそのまま返す
   - **三角測量：** 別の例のテストを足し、一般化せざるを得なくする
   - **明白な実装：** 答えが明らかなら、そのまま書く
4. **Refactor：** テストが通ったまま、重複を除き、名前を整え、認知複雑度の上限（5）に収める。テストも整える
5. TODOリストに戻る。リストが空になったら、その機能は終わり

### 2.2 守ること

- 失敗するテストがない状態で、プロダクトコードを書かない
- 一度に1つの TODO だけを扱う。別の問題に気づいたら TODO に書いて後回しにする
- Green の段階では設計をきれいにしようとしない。きれいにするのは Refactor で
- コミットは、テストがすべて通った状態（Refactor の後）で行う

### 2.3 Claude が進めるとき

TDD のサイクルは Claude に任せる。本人はコミットや PR でテストを読んで確認する。

- 機能に取りかかる前に、TODOリストを `it.todo` でテストファイルに書く（本人がテストファイルを見れば、何を確かめる予定かが分かる）
- Red のたびに対象のテストだけを実行し（`pnpm vitest run <ファイル> -t "<テスト名>"`）、失敗の理由を確かめてから実装する
- 仕様の解釈に迷ったら、推測で進めず design.md を確かめる。design.md で決まらないことは本人に聞く
- コミットの単位は、TODO を1つ以上終えて、`pnpm verify` が通った時点

## 3. テストの分類

「単体テスト／結合テスト」という呼び方は人によって指す範囲が違うため、**テストサイズ**（どこまで外部の資源を使うか）で分ける。

| サイズ | 対象 | 使ってよいもの | 書き方 | 量 |
|---|---|---|---|---|
| **Small** | `src/domain/` | なし（ファイル・時計・ネットワーク・Obsidian を使わない） | Vitest で純粋な関数を直接呼ぶ | 大半 |
| **Medium** | `src/app/` | 手書きの偽物（メモリ上の Vault、進め方を操作できる時計など） | Vitest。コマンド → 書き戻し → 再読み込みの流れを確かめる | 少し |
| **Large** | 本物の Obsidian | `dev-vault` | 手動の確認手順（6章） | ごく少数 |

- `src/adapters/` と `src/ui/` は自動テストの対象にしない。`adapters/` は Obsidian の API を呼ぶだけの薄い層に保ち、判断を含むコードは `domain/` か `app/` に寄せる。UI の見た目と操作は Large で確かめる
- テストファイルは `tests/` 以下に、`src/` と同じ層の名前で置く（`tests/domain/`、`tests/app/`）。設定ファイルを検査するテストは `tests/config/`。`src/` がディレクトリで分かれていれば、テストも同じディレクトリに分ける（`tests/domain/document/` など）
- ほかのディレクトリにあるテストの部品（偽物・arbitrary）は `@tests/...` で import する。`../` は禁止のため

## 4. 書き方

### 4.1 例によるテスト

- 1つのテストで確かめる振る舞いは1つ
- 準備・実行・確認（Arrange / Act / Assert）の順に書き、間を空行で区切る
- Markdown の本文はテンプレートリテラルでそのまま書き、入力と期待値を見比べられるようにする
- 日付や時刻は固定の値を使う。現在時刻に依存しない

### 4.2 プロパティベーステスト（fast-check）

具体例では思いつかない入力で壊れることを防ぐため、**性質**を確かめるテストを併用する。特に次の対象では必ず書く。

| 対象 | 確かめる性質 |
|---|---|
| Markdown の読み書き（AD-4） | どんな本文でも、読んでそのまま書き戻すと元と完全に一致する |
| コマンド（AD-4） | 並べ替え・状態の変更・追加の後も、固定行と TODO ブロック内のメモが失われない。TODO の件数が変わらない（追加以外） |
| 複製（design 7.8） | 複製後のファイルに `[x]` と作業時間の行がない。元のファイルが変わらない |
| 時間の計算 | 記録する分数が 0〜25 の整数に収まる |

- 失敗したときは fast-check が最小の反例を出す。その反例は、例によるテストとしても残す

### 4.3 テストダブル（偽物）

- モックライブラリ（`vi.mock` など）は使わない。`domain/` に定めた型（例：`Clock`）を実装した**手書きの偽物**を使う
- 偽物は `tests/` 以下の共通の場所に置き、テスト間で使い回す
- 「呼ばれたか」より「結果がどうなったか」を確かめる（メモリ上の Vault の本文を見る）

## 5. テストの質を測る

| 指標 | 道具 | 使い方 |
|---|---|---|
| カバレッジ | Vitest（v8） | `src/domain/` に 90% の下限。目的ではなく、テストの抜けを見つける道具として使う |
| ミューテーションスコア | Stryker | `src/domain/` のコードをわざと書き換え（変異）、テストが落ちるかを測る。下限 80%。手元で `pnpm mutation` を実行する（CI では回さない） |

- 生き残った変異（テストが落ちなかった書き換え）は、テストの確認が足りないか、不要なコードがあるかのどちらか。テストを足すか、コードを消す
- 機能を1つ書き終えたら `pnpm mutation` を実行する。差分だけを測るので2回目以降は速い

## 6. 手動の確認手順（Large）

`dev-vault` を Obsidian で開き、`pnpm dev` を実行した状態で行う。リリース前と、UI や `adapters/` を変えたときに回す。

| # | 確かめること | 期待する結果 |
|---|---|---|
| L1 | 今日のファイルがある状態でボードを開く | 3列に TODO が並び、予定がタイムラインに出る。書式外の行は表示されない |
| L2 | 今日のファイルがない状態でボードを開き、「今日のファイルを作る」を押す | 「今日のファイルがありません」の下にボタンが出る（過去の日には出ない）。押すと直近の過去ファイル（週末を挟んでも）の `[ ]`・`[/]` が `[ ]` で順番どおりに複製され、そのままボードに出る。見積もりとメモの子の行は残り、作業時間の行・完了・書式外の行・`events` は複製されない。元のファイルは変わらない |
| L2a | 過去のファイルがない、または未完了が0件で「今日のファイルを作る」を押す | `date` だけの frontmatter のファイルができ、空のボードが出る。TODO のフォルダがなければフォルダごとできる |
| L2b | ボードがファイルなしのまま、エディタなどで今日のファイルを先に作ってから押す（ボードが読み直す前に押す） | 上書きされず「もうあった」と知らされ、あったファイルが出る |
| L3 | カードを並べ替える・列を移す | Markdown の行の順番と記号が変わる。書式外の行とメモが元の位置・カードに残る |
| L4 | カードを着手中に動かし、25分待つ | 通知と音が出て、`25分 ポモドーロ` が記録され、カードは着手中に残る |
| L5 | 計測中に Obsidian を閉じて開き直す | 開始時刻から再計算され、続きから計測される |
| L6 | Markdown をエディタで直接編集する | ボードに反映される。編集中に計測が捨てられない |
| L7 | 作業時間を修正する（M2） | 分数の変更・追加・削除が子の行に反映される |
| L8 | 過去の日を開く | 閲覧と作業時間の修正だけができる |
| L9 | Obsidian のテーマをライト／ダークで切り替える | ボードとダイアログが追従する |
| L10 | ボードを開いたまま設定を変える（TODO のフォルダ、就業時間、休憩の追加・削除、満了の音） | ボードがすぐに読み直され、タイムラインとヘッダーの可能な数が変わる。正しくない入力は欄の下に問題が出て、保存されない。音をオフにすると満了で音だけが鳴らない |

## 7. 必ず押さえるテストの観点

| 対象 | 観点 |
|---|---|
| 読み書き | 読んでそのまま書き戻すと元と完全に一致する（書式外の行、空行、改行コード、インデント） |
| コマンド | 各コマンドの後も固定行が元の位置に残る。TODO ブロック内のメモは並べ替え後もそのカードの下にある。「今日やる」が0件のときの先頭・末尾への移動と追加 |
| タイマー | design 8.1 の表の各行（25分の満了、中断、完了、別のカードへの切り替え、停止中の切り替え、今日やるへ戻す）。スリープ後の再計算。1分未満を記録しない |
| タイマーの確定 | 満了と「完了にする」が重なっても記録は1行だけ。`[/]` が一時的に崩れても保留にして、元に戻れば計測を続ける |
| 複製 | 直近の過去ファイルを選ぶ（週末を挟む）。状態を `[ ]` に戻す。見積もりを残す。作業時間の行をコピーしない。元のファイルを変えない |
| 集中できる時間 | 予定と休憩の重なり。就業時間外。端数の切り捨て |
| 他の日 | 過去の日は作業時間の修正だけ。未来の日は開けない（design 8.3） |
